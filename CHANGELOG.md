- 2026-09-06 — fix(query): key the response cache on the full caller hint, not its first 80 characters (#254) — `responseCacheKey` truncated `callerHint` to 80 chars to bound key size. The hints `src/lib/detect-caller.ts` emits run 68-106 characters — six of ten are already at or past the cap on their own — so once the 18-character `; shown_projects: ` prefix is appended, the slug list began at index 86 at the very least: past the cap for every hint without exception. The slug list is the only part that varies between two follow-ups, so it was always the part discarded. Both collapsed to the same key, so a visitor asking "what else?" after seeing one set of projects could be served the answer cached for a visitor who had seen a different set. This lands on the highest-traffic path: per `summarize_observed_queries`, "Show recent work" is the most common question by a wide margin (91 of 353 HTTP queries over 97 days), and that starter chip is exactly the progressive-disclosure entry point. Intermittent rather than permanent — bounded by the cache's own 5-minute staleness window and 200-entry LRU — which is likely why it went unnoticed. Note the hint reaches the key by two routes: it selects tone AND carries `shown_projects`, and `sanitizeCallerHint`/`parseShownProjectSlugs` already treat that suffix as load-bearing; only the cache key discarded it. Fixed by hashing the hint instead of truncating it — bounded key size, no collision, and the key no longer embeds raw caller-supplied text at all. The `.toLowerCase().trim()` normalization is kept and hashed WITH the value: only the cap was the defect, and hashing the raw string would additionally split "Recruiter" from "recruiter" (both reachable from caller-supplied `context`), trading a correctness bug for a hit-rate regression. The format change orphans existing entries, which is harmless — the cache is in-memory with a 5-minute staleness bound, so the cost is one cold start. Found by the Copilot review agent during a re-review of #253, which pushed a fix directly onto that PR's branch; reverted there as out of scope (#253 is the streaming path, this is the non-streaming response cache, and coupling them would mean a revert of #253 silently reverting this too) and reworked here with the normalization corrected and tests built on the three real production hints rather than a synthetic over-length string — mutation-verified against the pre-fix truncation, against the raw-hash variant, and against a merely-larger cap. A second review pass corrected the hint-length claim above (originally written as "68-73 chars", which was measured from only the three hints sampled) and found a residual instance of the same bug class: the key hashes the LOWERCASED hint while `buildQueryPrompt` compared `shown_projects` slugs case-sensitively, so `Brew-Guide` and `brew-guide` shared a key while only one of them filtered anything — the comparison is now lowercased on both sides

- 2026-08-12 — feat(match): JD-driven extraction replaces the fixed experience/domain rubric, closing the compression #241 flagged but didn't fix (docs/plans/match-quality-extraction.md) — `experience`+`domain` used to contribute a near-constant `0.41 ± 0.03` to `fit_score` regardless of actual fit, because `skills` extracted what a JD actually asked for (`required_skills_extracted`) before scoring it, while `experience`/`domain` were scored against a fixed six-sub-factor rubric applied identically to every JD — the model filled in plausible defaults for axes nobody asked it to reason about. `src/lib/score-match.ts` now extracts a per-JD list of qualities (skill, experience, or domain — whichever the JD actually raises) with a `jd_importance` (`must_have`/`preferred`), then scores each with a `verdict` (matched/partial/missing) and an `evidence_grade` (verified/claimed/absent — verified means backed by a dated project's `git_evidence` or an unambiguous employment range, not just prose). `fit_score` is a weighted average over that list, bounded 0..1 by construction: `skillsScore`'s #240 fix — `max(requiredWeightSum, scoredWeightSum)` as the denominator — is generalized from a uniform per-skill weight to a per-quality `jd_importance` weight and retired as a separate function (every category now shares one `qualityScore`); `tests/score-match-bounds.test.ts` proves the generalization reduces to #240's exact original results at uniform weight/evidence, not just that it's separately bounded. Validated against the actual production failure, not just unit tests: a 21-case held-out JD set (`scripts/eval/match-eval-cases.ts`, `npm run eval:match`) that was previously unusable — it was built for the OLD fixed-axis rubric before this redesign — now drives `fit_score` from `sd 0.053` (the reported bug) to `sd 0.215` across a `0.05–1.00` range on a live run, with 27/27 held-out expectations passing. Two rounds of live-model spiking against 3 models (`google/gemma-4-26b-a4b-it`, `google/gemini-3.6-flash`, `openai/gpt-5.6-luna-pro`) surfaced and fixed a rubric-tightening regression before it shipped: an earlier fix for over-eager domain/scale extraction ("Fortune 500 scale" getting extracted from mere company description) accidentally suppressed extraction of role *scope* (individual contributor / tech lead / manager) too, since both were phrased as "context" under the same instruction — fixed with an explicit carve-out ("role scope is not company context"), confirmed by rerunning the previously-failing cases live. A genuinely ambiguous axis (does a JD's stated company size imply a candidate requirement, or is it just description?) is treated as a feature of the held-out set, not a bug to keep tuning away — `tests/match-quality-consistency.test.ts` (`npm run test:match-consistency`, live model calls, not in `test:unit`) asserts anchors agree fully across 5 repeated runs while that case is explicitly allowed bounded disagreement, per the same-model/cross-model/phrasing-invariant dimensions the spike identified as actually varying. Found and fixed in the same pass: `generateWithLengthRetry` (moved from `src/routes/query.ts` to `src/lib/ai.ts` so both callers can share it) computed its retry cap as `min(cap * 2, 2048)` — harmless for `/query`'s smaller starting caps, but silently a no-op retry for `/match`'s `2048`-token starting cap, which is exactly what caused `gemini-3.6-flash` to return `null` on truncation during D6's own test run; now takes an explicit `retryCeiling` per caller. The private `/mcp` server's `score_match` tool (`src/routes/mcp.ts`) rendered the old fixed `scoring.skills/experience/domain` shape into its summary text — a downstream consumer the original design missed entirely, caught only because the code no longer compiled against the new `MatchScoring` type; rewritten to group `scored_qualities` by category. `src/routes/openapi.ts` and `README.md`'s "Agentic job match methodology" section (which stated the exact fixed 50/30/20 weighting this removes) are updated to describe the extraction-first design. **Deliberately out of scope for this change, tracked as explicit follow-ups:** `job-hunt-agent`'s `apply:batch` threshold needs re-validation against the new `fit_score` distribution (the scoring math changed even though the response shape it reads — `fit_score`/`matched`/`gaps`/`verdict`/`recommended_action` — did not), and `resume-agent-web`'s `MatchResume.tsx` destructures the *old* fixed `scoring.skills.score`/`.experience.score`/`.domain.score` shape directly and will break at runtime until it's updated to render the new dynamic quality list — both are separate repos, separate PRs, sequenced after this ships to production.

- 2026-08-10 — fix(match): `fit_score` could exceed 1.0 because the skills sub-score had no upper bound (#240) — `/match` returned `fit_score: 1.37`. The composite weighting was never the problem: `0.5(1.88) + 0.3(1.00) + 0.2(0.67)` reproduces it exactly, and `experience` and `domain` were both in range. The unbounded input was `skills.score`, which divided *what the model classified* by *what the model extracted* — `(matched + 0.5 × partial) / required_skills_extracted.length` — with nothing tying those two lists to each other. Measured against live output, they disagree on half of runs: one JD yielded 4 extracted requirements against 9 classified skills (1.88), another 14 against 16, and the rubric also counts responsibilities as required skills ("Design core UI features", "Collaborate on backend APIs"), which inflates the denominator in the other direction. New `skillsScore` divides by `max(|required|, matched + partial + missing)`, which is bounded by construction since `credit ≤ matched + partial + missing ≤ denominator`, and needs no clamp, no shape change, and **no prompt edit**. `max()` rather than either list alone because each single-list choice is gameable in one direction: `|required|` alone lets the buckets overflow it — the reported bug — while the bucket count alone lets the model omit a requirement it would have to score badly, shrinking numerator and denominator together and inflating the score *without ever leaving 0–1*. That second failure was not theoretical: a prototype collapsing both lists into one `{skill, verdict}` array turned a visible 1.06 into a clean-looking 1.00 by silently dropping 4 of 9 requirements, and produced zero `missing` entries on 3 of 4 JDs — strictly worse, because nothing flags it. Aligning the two lists by name was also rejected, since the same model emits `"State management libraries (Zustand, Redux, MobX)"` on one run and the three names separately on the next, which any string match scores as three false missings. The old `|| 1` fallback survives but is no longer a hazard: it now fires only when both lists are empty, where the numerator is necessarily 0 too. **What this does not fix, stated plainly so the issue is not read as closed:** it is a range fix, not a deflation. Recomputed across all 112 stored shortlist entries in `job-hunt-agent`, 109 still qualify at 0.65 and 70 of 72 still clear 0.76 — only 19 entries (17%) move at all, by a mean of −0.105. The inflation has a different cause: `experience` has p50 exactly 1.00 with sd 0.053 across those 112 entries, so 30% of the total weight carries almost no discriminating signal, and `experience + domain` together contribute a near-constant 0.41 ± 0.03 — making `fit_score ≈ 0.41 + 0.5 × skills`, with roughly the bottom 40% of the scale unreachable. That is a rubric-design problem needing eval coverage before anyone edits the prompt, and it is tracked separately. Also **not** a regression from the recent `job-hunt-agent` work: out-of-range sub-scores appear in stored shortlists on 2026-07-27, 08-04 and 08-06, two weeks before #45/#46/#47 landed on 08-10; those changes widened intake from 11 to ~74 scored listings per run, which raised exposure ~7× and made a pre-existing defect visible rather than creating one. Separately, `src/routes/openapi.ts` documented `fit_score` as *"Overall fit percentage 0–100"* — the machine-readable schema, on a surface whose premise is machine explorability, misstating the range of the exact field this fix bounds, undetected because every real value is valid under both readings; now `0–1` with explicit `minimum`/`maximum`. 6 new unit tests (`tests/score-match-bounds.test.ts`), added to the explicit `test:unit` list — it is not a glob. Deliberately out of scope: sub-factor validation (measured valid 8/8 on live output; never fired) and an `n = 0 → null` path (`job-hunt-agent/src/scout-mail.ts` has no per-item catch, so a null aborts an entire unattended run rather than skipping one listing)

- 2026-08-07 — fix(db): `npm run db:push` aborted on the first migration, and unnamed indexes had silently duplicated (#237) — `scripts/db-push.ts` has no migration-tracking table; it replays every `.sql` in filename order under `ON_ERROR_STOP=1`. That design is fine but requires every migration to be re-runnable, and five were not. The earliest sorted first, so `create table public_profile` failed with "relation already exists" on line 4 of file 1 of 16 and **nothing after it ever ran** — every migration since had to be applied by hand, which is how the #235 privacy guard nearly shipped without its SQL. Fixed per statement type: `create table if not exists`; `drop policy if exists` / `drop trigger if exists` before create (PostgreSQL has neither `create policy if not exists` nor `create trigger if not exists`); and `on conflict (id) do nothing` on the `public_profile` seed row. Separately, eight indexes were declared without a name. Unnamed `create index` never errors on replay — PostgreSQL just auto-generates a fresh name — so instead of failing loudly it had silently built byte-identical second copies under `…_idx1`: **~32 MB, dominated by a duplicate 31 MB HNSW vector index on `thoughts` that was being re-maintained on every insert and update.** They are now named with the identifiers PostgreSQL originally assigned, so `if not exists` matches what is already there rather than adding a third copy — the trap in the obvious fix — and `20260807000000_drop_duplicate_indexes.sql` removes the existing duplicates, itself guarded with `if exists` so it is a no-op on a fresh project. Duplicates were confirmed identical by normalising `indexdef` and grouping, not by trusting the naming convention. Verified against production: two consecutive `db:push` runs both exit 0 with zero errors, indexes 27 → 19 (exactly the eight duplicates), `public_profile` still 1 row, `thoughts` still 4181, canonical indexes / policies / trigger all intact, and the #235 privacy guard survives the replay

- 2026-07-29 — feat(observations): first-class `authored` signal separating hand-written notes from machine-generated entries (#222) — `GET /observations` mixed two classes of item under one `type: "observation"`: the dated authored reasoning trail the endpoint's own `note` advertises, and machine writes that happen to share the type (the nightly sync's `VERSION DRIFT` warnings, `src/routes/resume.ts`'s `RESUME_RUBRIC_FAILURE` telemetry). `?type=` couldn't separate them, so the frontend was filtering client-side on a topic/length heuristic — a consumer guessing at producer shape, and the reason per-observation pages were deferred. Every item now carries `authored: true|false`, with a matching server-side `?authored=1|0` filter applied *before* the `limit` slice (so `?authored=1&limit=25` returns 25 authored notes, not the authored remainder of a mixed page). The flag comes from an **allowlist** of authored `metadata.source` values (`AUTHORED_THOUGHT_SOURCES = ['mcp']`, the private MCP `capture_thought` path) rather than a denylist of machine ones: a denylist has the same failure mode as the heuristic it replaces — a machine writer added later silently passes as authored — whereas an allowlist leaves it `authored: false` until explicitly listed. A missing `source` is likewise not authored, which matches the data (all 148 source-less public rows in the live table were machine telemetry from writers predating the convention; zero authored notes lack it). **Additive and non-breaking**: the default listing returns both classes exactly as before, and the `authored` echo appears in the envelope only when the filter was requested — which doubles as a capability probe on the call a filtering client actually makes, since `?authored=1` against an older deployment returns the unfiltered list with a 200 and plausible JSON, and key-absence is the only way to tell that from an honored filter. Keeping the default unchanged also leaves the documented `?type=reference` escape hatch working: every ledger row is machine-written, so an authored-only default would have emptied it rather than filtered it. Two additive envelope fields, `total` (how many matched) and `truncated` (whether `limit` cut it short), so a consumer can distinguish a complete page from a capped one instead of inferring it from `count`. `?limit` ceiling raised 100 → 500 — separately decided: the consumer is a single server-rendered page with no pagination UI that wants every authored note in one request, and the query already fetches up to `FETCH_CEILING` rows, so a wider in-memory slice costs nothing. The handler now warns when a fetch fills the `FETCH_CEILING` window instead of relying on a comment, which immediately surfaced a pre-existing and unrelated issue: the `reference` ledger is at 3,485 rows against a 1,000-row window, so `?type=reference&topic=…` already misses older matches. The stale comment claiming the ceiling sits above the largest type is corrected; the paging fix it calls for is deliberately out of scope. openapi schema + README updated, 6 new unit tests
